# Generic front template by default, NEOCORE as a preset chosen by name

Objective: the template runs on its generic core ports unless the project opts into NEOCORE, chosen by name like ms-template's `TEMPLATE_PRESET`; every integration stays a removable piece. Branch: `feat/template-preset` (mf-template, then front-template by merge). Delivery: single PR per repo. Runner: `bun run lint`, `bun run format:check`, `bun run build`, `bun run build:federation`, `bun run test`.

- S5 (decision for S2): run modes stay as they are — `start`/`build` = plain SPA (default), `start:federation`/`build:federation` = micro-frontend remote. Verified on the base: `build` emits no `remoteEntry.json`, `build:federation` does.
- S6 (decision for S3): `TEMPLATE_PRESET=generic|neocore` (default `generic`) in `.env`, baked by `load-env.js` into `environment.templatePreset`; an unknown value fails the build with a clear message; `neocore` requires `SECRET_KEY`. One file, `src/app/template-preset.ts`, maps the name to providers (`generic` → none, `neocore` → `provideNeocoreHost()`) and is the only place outside `integrations/` that imports an integration. `app.config.ts` and every exposed route call `provideTemplatePreset()`.
- S7: the generic test kit (`src/testing/`) does not import any integration; the NEOCORE test doubles live and are tested inside `src/app/integrations/neocore/`.
- S8: removing NEOCORE = delete `src/app/integrations/neocore/`, its entry in `template-preset.ts` and its three dependencies; build and tests still pass. Docs say so.

- S9 (user, 2026-11-23, verbatim): "dale, pushea y abre los MR, y agrega las 4 piezas". The four pieces, each generic, with a safe default and removable in one place:
- S10 HTTP error notifications: `errorNotificationInterceptor` (in `src/app/shared/interceptors/`) catches every `HttpErrorResponse`, calls `Notifier.error(toUserMessage(error))` and rethrows the same error. A request opts out with the `HttpContextToken` `SKIP_ERROR_NOTIFICATION` (for callers that show their own message). A 401 also calls the core port `SESSION_EXPIRED_HANDLER` (`src/app/core/session-expired.ts`, `InjectionToken<() => void>`, default no-op). Wired by default in `provideAppHttpClient()` (standalone only: a hosted remote uses the host's HttpClient). The example module stops showing its own error toast (the interceptor does), so a generated module gets one message, not two.
- S11 Session guard: `sessionGuard(loginPath = SESSION_LOGIN_PATH_DEFAULT)` (`src/app/shared/guards/session.guard.ts`, default `/login`) lets the route through when `AUTH_TOKEN_PROVIDER` returns a usable bearer token (`isUsableBearerToken`); otherwise it calls `Notifier.warning(SESSION_REQUIRED_MESSAGE)` and returns a `UrlTree` to `loginPath` with `returnUrl` = the attempted URL as query param.
- S12 Global error handler: `AppErrorHandler` (`src/app/core/app-error-handler.ts`, `provideAppErrorHandler()`) logs to `console.error` as Angular does and calls `Notifier.error(toUserMessage(error))` for any error that is not an `HttpErrorResponse` (those belong to S10, never notified twice). Registered in `app.config.ts` only (a hosted remote runs the host's handler).
- S13 Request id: `requestIdInterceptor` adds `x-request-id` (`crypto.randomUUID()`) to requests whose URL starts with `environment.apiUrl`, unless the request already carries one; other origins get nothing (no header leaked to third-party APIs, no new CORS preflight for them). Same header name as ms-template's `REQUEST_ID_HEADER`, so front and back logs correlate. Wired by default in `provideAppHttpClient()`.
